「これ作れるかな?」と思っている部分を 1 つ選んで、本格実装の前に AI コーディングで先に動かしてみる。**「動いた」も「動かなかった」もどちらも収穫**（動かないなら設計変更の根拠になる）。

## 手順 1 — spike 仮説（投げる前に自分で 3 行書く）

- 確かめたい: 【何が動けば OK か】
- 動けば言える: 【ピッチ・計画で何と言えるようになるか】
- 動かなければ困る: 【何を再調査・設計変更することになるか】

## 手順 2 — AI に貼るプロンプト

【 】を自分の内容に置き換えてから、コーディング AI に貼る。

```text
【確かめたいことの最小コード】を作ってください。

要件:
- 【技術スタック。例: Next.js の API Route】で【何をする。例: 外部 API に 1 リクエスト送る】
- 確認対象だけに絞った最小構成（認証・UI の見栄え・エラー画面は不要）
- 値はぜんぶ固定値・ハードコードで OK（例: 送信先 ID は固定、メッセージは固定文）
- 動いたか失敗したかが分かる詳細ログを出す
- 必要な事前準備（アカウント登録・API キー取得など）があれば、手順を先に箇条書きで教えて
- この最小コードの確認で終了。リファクタ・追加機能・本実装は続けない
```

> 欲張らない。1 セッションで 1 つの不安だけ。コア機能 1 つでよい（見栄えは Chapter 2 で整える）。

## ✅ 最終アウトプット（自分の言葉で書く）

### 最大の不安に思っていた技術ポイント（1 つだけ）

- LINE Messaging API を使って、LINEミニアプリ/ボットから固定メッセージを送信できるかどうか

> 例: 〇〇 API で〇〇できるか / データ取り込み / 認証フロー / コスト試算

### spike 仮説（3 行）

- 確かめたい: Node.js から LINE Messaging API の送信エンドポイントに対して、固定メッセージを送る最小コードが動くか
- 動けば言える: 「LINE連携によるメッセージ送信は技術的に実装可能で、PoCで送信機能を検証する土台ができた」と言える
- 動かなければ困る: 「サービスをLINE連携前提にする設計は再検討し、別の送信UXやチャネルを検討する必要がある」と言える

### 結果（動いた / 動かなかった ＋ 学び）

- 結果: 構成済みの最小コードが正常に構文チェックを通過し、LINE Messaging API の送信パターンが実装可能であることが確認できた。実際の送信はAPIキー・LINEチャネル登録が必要で、本環境では実行していない。
- 学び: LINE送信は固定メッセージの構成とHTTPリクエストだけで済むため、実装面では大きな障壁は低い。ただし、APIキー取得・チャネル登録・ユーザーID取得などの事前準備が必須である。

> 例（動いた）: 通知が届いた → ピッチで「技術検証済」と言える。ただし前提条件 〇〇 を発見
> 例（動かなかった）: API 制約 〇〇 が発覚 → 設計変更が必要

### ⚠ 弱さ（→ Stage 19 検証へ）

- 今回の spike で検証したのはコード構成と送信リクエストの形式であり、実際のLINE送信成功やユーザー側の受信体験、本番の認証フローは未検証である。

> 例: 「本番規模（100 ユーザー同時）は未検証」のような、今回の spike で確かめきれなかった範囲
