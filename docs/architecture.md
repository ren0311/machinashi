# Architecture

## 1. 目的

待ちなしは、待ち合わせ中に連絡が途切れたときに不安を感じるユーザーが、すぐに安心確認メッセージを選んで送信できるサービスを提供する。

今回の MVP は「待ち合わせの不安を軽くする」ことに集中し、最低限の UI とロジックで検証できる構成にする。

## 2. 設計方針

- シンプルな 1 画面中心の体験にする
- まずは LINE 連携を前提にしつつ、MVP では軽量に実装する
- 認証、テンプレート管理、送信履歴の 3 層を最小構成で扱う
- 仕組みよりも、ユーザーがすぐに使える体験を優先する

## 3. アーキテクチャの全体像

```text
[Client App]
  ├─ Auth / Session
  ├─ Waiting state screen
  ├─ Template selection screen
  ├─ Send confirmation screen
  └─ History / sent records
        ↓
[API Layer]
  ├─ user profile / auth
  ├─ template list / create
  ├─ send action
  └─ history read
        ↓
[Data Store]
  ├─ users
  ├─ templates
  ├─ sent_messages
  └─ settings
```

## 4. コンポーネント構成

### Frontend
- Web アプリまたはアプリのプロトタイプとしての UI
- ユーザーが最短でテンプレートを選ぶことができる画面を持つ
- 画面は以下の 4 つを基本とする
  1. 待ち合わせ状態の表示
  2. テンプレート一覧
  3. メッセージ送信確認
  4. 送信履歴

### Backend
- ユーザー情報の取得
- 保存済みの安心確認テンプレートの取得
- 送信内容の保存
- 送信履歴と利用状況の管理

### Data model
- User
  - id
  - name
  - created_at
- Template
  - id
  - user_id
  - title
  - text
  - category
  - created_at
- SentMessage
  - id
  - user_id
  - template_id
  - recipient
  - message_text
  - sent_at
  - status

## 5. 主要なユーザー体験フロー

### フロー 1: 直前の待ち合わせで不安が生じる
1. ユーザーが待ち合わせ状態を開始する
2. 相手から返信が来ない状態を確認する
3. 事前に用意されたテンプレートから選ぶ
4. 送信して安心感を得る
5. 履歴から再利用できる

### フロー 2: すぐに使う
1. アプリを開く
2. 送る文面を選ぶ
3. 相手に送る
4. 送信内容を確認し、次の待ち時間を安心して過ごす

## 6. MVP に必要な最小機能

- ログインまたは簡易ユーザー識別
- テンプレート一覧表示
- テンプレートの選択
- 送信アクション
- 送信履歴の表示
- ステータスの見える化

以下は MVP では不要:
- 位置情報共有
- 決済
- 予約管理
- グループチャット運用
- 高度な AI 自動返信

## 7. 技術選定の考え方

### 可能な構成案

#### 案 A: Next.js + Supabase
- UI 開発が速い
- 認証とデータ保存が簡単
- MVP の検証に適している
- 予算と運用の面でも管理しやすい

#### 案 B: Vite + Firebase
- 早く動かせる
- 簡単にプロトタイプを作れる
- ただし、データ設計と拡張の整理が必要になる

#### 案 C: Flask or Node API + PostgreSQL
- しっかりした構成にできる
- ただし、MVP のスピードと工数が増えやすい

### 推奨
- MVP では「Next.js + Supabase」または「Vite + Firebase」で始めるのが適切
- 初期段階では、実際に価値を検証することが最優先であるため、機能を絞って運用しやすい構成を採用する

## 8. MVP での責務分離

### Client
- 画面表示
- テンプレート選択
- 送信確認
- 履歴の表示

### Server / API
- 認証状態の保護
- テンプレート取得
- 送信ログの保存
- ルール整合の確認

### Database
- ユーザーデータ
- テンプレートデータ
- 送信履歴
- 制約や検索条件の保持

## 9. リリース時の目標

MVP の成功条件は、以下を満たすこととする。

- ユーザーが「今すぐ使える」と感じる
- 送信前後の体験に迷いがない
- 待ち合わせの不安が軽減されたと感じられる
- 「この機能をもっと使いたい」と思える

## 10. 次の一手

次の段階では、以下を具体化する。

- 画面一覧を作る
- 主要なユーザーフローを 1 本に絞る
- 最小限のデータ構造を定義する
- 最小実装の技術スタックを決める

これができれば、MVP の実装に着手できる状態になる。
